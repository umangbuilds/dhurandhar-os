## Title
Merchant Disbursement, T+1 Settlement (v1.0)

## Goal
Onboarded merchants receive net settlement to their registered bank account on T+1 (one business day after the user's debit clears), via a payment aggregator integration with a tiered MDR schedule.

## Non-goals
- Instant (T+0) settlement — explicitly out of scope at v1.0; will be considered in v1.1 with explicit fee.
- International settlements — INR-INR only at v1.0.
- Marketplace settlement (split between multiple merchants per transaction) — out of scope; v1.0 is single-merchant.
- Cash-on-delivery reconciliation — not applicable to this product.

## User journey
1. Onboarded merchant logs in to the dashboard.
2. Merchant accepts a customer payment via the payment aggregator (tokenised card / UPI / netbanking).
3. Customer's debit clears at the aggregator within ~30 seconds.
4. At T+1 (next business day, 14:00 IST cutoff), aggregator initiates net settlement to merchant's registered bank account.
5. Merchant sees settlement reflected in dashboard's "Settled" view by 18:00 IST on T+1.
6. Merchant downloads the daily settlement report (CSV) for accounting / GST reconciliation.

## Acceptance criteria
- **AC1:** Given a successful customer payment at T+0 14:30 IST, when settlement runs at T+1 14:00 IST, then the merchant's bank account is credited with `(payment_amount - mdr - gst_on_mdr)` by 17:00 IST on T+1.
- **AC2:** Given a partial payment failure (e.g., aggregator confirms but bank rejects), when reconciliation runs at T+1 18:00 IST, then the failure is logged, alerted to ops, and the user is auto-refunded within 48 hours.
- **AC3:** Given a duplicate webhook delivery for the same `transaction_id`, when the system processes the duplicate, then the second processing is a no-op (idempotency-key constraint enforced at the database level).
- **AC4:** Given the merchant has not provided a registered bank account, when a payment is accepted, then the system rejects the payment at the gateway level with a clear error message ("merchant not configured for settlement").
- **AC5:** Given the merchant requests their settlement report, when the dashboard loads the report, then all settled transactions for the requested date range are returned within 3 seconds for ranges up to 30 days.

## Money flow diagram

```
[User wallet / card / UPI] --debit ₹1000-->  [Aggregator escrow]
                                                      |
                                                      | T+1 14:00 IST
                                                      v
                                              [Aggregator settlement]
                                                      |
                                                      | net = ₹1000 - 2.5% MDR (₹25) - 18% GST on MDR (₹4.5)
                                                      v
                                              [Merchant bank account: ₹970.5]

States:
  - debit_pending     (at user, before aggregator confirms)
  - escrow_held       (at aggregator, between debit clear and settlement run)
  - settled           (at merchant)
  - reversed          (refund / chargeback path — separate flow, not in this PRD)

Fees (v1.0):
  - 2.5% MDR (merchant discount rate) — paid to aggregator
  - 18% GST on MDR — paid to government via aggregator
  - ₹0 user-facing fee at v1.0

Failure paths:
  - Aggregator webhook timeout    → retry queue (exponential backoff, max 5 attempts over 30 min)
  - Aggregator returns settlement_failed → reverse to user wallet, log for ops review
  - Merchant bank rejects deposit → settlement re-tried next business day; ops manual review after 3 failures
  - User initiates chargeback     → standard chargeback flow (not in v1.0 spec; follows aggregator's NPCI dispute resolution)
```

## Reconciliation ownership
- **Daily reconciliation:** automated job at T+2 09:00 IST cross-checks aggregator-reported settlements against our database. Discrepancies > ₹100 logged and routed to **Ops Lead (Priya, Bengaluru)**.
- **Weekly reconciliation:** Ops Lead manually reviews the discrepancy queue every Friday 14:00 IST and signs off.
- **Aggregator-side disputes:** Ops Lead is the named escalation contact with the payment aggregator's account manager.

## Failure modes
- **Webhook duplicate delivery.** Idempotency key `txn_<aggregator_txn_id>` enforced via unique constraint on the database. Duplicate webhook → no-op.
- **Webhook out-of-order.** State machine accepts only valid transitions: `debit_pending → escrow_held → settled` or `escrow_held → reversed`. Out-of-order messages logged and dropped.
- **Webhook signature failure.** Reject. Log. Alert ops if rate exceeds 1% over 1-hour window.
- **Webhook timeout.** Retry queue, exponential backoff, max 5 attempts over 30 min. After exhaustion, manual reconciliation via Ops Lead.
- **Database partial write.** All settlement state transitions wrapped in DB transaction. Rollback on partial failure.
- **Aggregator API down at settlement run.** Settlement re-attempted at next scheduled run (daily). Operator dashboard shows "settlement pending — aggregator unavailable" status.
- **Merchant bank rejects deposit.** Aggregator retries per their policy. After 3 failures, ops manual review and merchant notification.

## Test plan
- **Unit:** state machine transitions, idempotency-key constraint, MDR + GST calculation.
- **Integration:** aggregator webhook handler with mocked aggregator responses (success, failure, duplicate, timeout).
- **Contract:** API contract with the aggregator (payload schemas, signature verification).
- **End-to-end:** full happy-path settlement on a sandbox aggregator integration. Run at T+0 sandbox time; settlement at T+1 sandbox time.
- **Load:** 100 settlement runs in parallel; verify database constraint prevents duplicate-key races.
- **Failure injection:** kill webhook delivery mid-flow; verify retry queue picks up and idempotency holds.
